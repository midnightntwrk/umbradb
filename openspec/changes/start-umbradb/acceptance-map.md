# Acceptance map — START-UMBRADB: UmbraDB as a library

Each criterion of `acceptance.md` (L1 … L68, the rewritten `core-arch` criteria of its §9, and A66's schema additions)
mapped to the tests that prove it, and each `[NEG]` criterion's negative control to its test and to where it was seen
failing for its own reason with the fault put back. Written in `tasks.md` 9.3, on the tree the verification ran on
(`tasks.md` §9 records the runs). A test is cited as `file` › «describe» › «test», each title exactly as the source
writes it (`$name`, `%s` and `${…}` are the parameters a parameterized title fills in; a `describe.each` over the
backends runs on PostgreSQL 18 in Docker and on PGlite). Every cited title is checked to exist in its file, and every
test it names to have passed in 9.2's conformance run (the one skip is A162's PostgreSQL-only case on PGlite, noted in
its row).

**How a negative control is seen failing.** Two kinds of evidence, named in the last column:

- **C** — the committed control. It runs in every full run and passes only because the criterion's oracle reports the
  fault the control puts back (a test seam, a fixture copy, the check removed on one path): a passing control is the
  oracle seen failing. Each **C** below passed in `tasks.md` 9.1's full run and in 9.2's conformance run (its JSON
  report lists every cited control `passed`).
- **F** — the fault also put back in the source (or the criterion's tests run on the tree before the change) during the
  build, with the count that failed; recorded in the task's **Done** line of `tasks.md` and in the build's phase notes.
