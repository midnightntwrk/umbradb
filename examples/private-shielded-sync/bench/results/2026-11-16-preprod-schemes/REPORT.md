24 benchmark runs, 4 snapshot sizes (69,329, 100,000, 1,000,000, 2,000,000 entries), both schemes at each, 32 queries per call. Section 1 is generated by `examples/private-shielded-sync/bench/bench.ts compare` from the runs' `results.json` files under `runs/`; the sections after it were written for this report and given to the command with `--notes`.

## 2. Setup and method

- **Data:** Preprod at height 3,439,524: 69,329 shielded outputs, 57,812 nullifiers, `pathSplit` k = 16 (read
  records 98 bytes, path records 512 bytes, nullifier entries 40 bytes), `queriesPerCall` 32. A padded snapshot (a
  debug mode, Q57 of spec 00053) holds the real records among random entries: its scan file and its three tables all
  have the padded count of entries; the wallets' coins are the real ones.
- **Server:** the run's own UmbraDB process (`umbradb run`, Node.js 24.9.0) from the checkout `poc-ipir-run` at
  `c372e0aa`, database container `ipir-pg`, module setting `threads` 6. SimplePIR builds and answers on the module's
  6 worker threads. IPIR+SP builds and answers in the native add-on: each request on rayon's global pool (16 threads
  on this machine; the add-on sets no limit), the 32 requests of a call one after another. The thread budgets differ;
  the server times below are each scheme's as deployed here, not per thread.
- **Wallets:** A (10 coins, 7 unspent) and B (1 coin), each a fresh client in the benchmark's process (empty cache),
  one after the other, over HTTP on 127.0.0.1. Client threads 8: the scan and SimplePIR's wallet multiply use 8 worker
  threads; IPIR+SP's wallet WebAssembly runs on one thread. After each sync the wallet reads the lower paths of its
  unspent coins in blocks full at the snapshot, as `send` does (`lowerPathsByPir`: A reads 4 paths, B none, so B's call
  carries 32 random rows); every path read is checked against its block's root.
- **Method:** `run-pair.sh` (beside this report) runs one repetition at one size: the benchmark asks the
  server for a SimplePIR snapshot, then an IPIR+SP one, at 3,439,524 (`--build-height`, `--scheme`, `--padding`), and
  measures both wallets against each. Three repetitions per size, 24 runs. Each figure is the median over its samples,
  with the smallest and largest value and the number of samples n: a build or snapshot figure has one sample per
  repetition (n 3), a call figure one per wallet per repetition (n 6). Every build of a size and scheme gave the same
  snapshot identifier (the builds are deterministic), so the byte figures have no spread.
- **Memory:** the server process's resident size by `ps -o rss=` every 200 ms (before the build request, its peak until
  the snapshot is served, the median of its 250 ms peaks 1 to 3 s after) and the build's own statistics (sampled every
  10 ms in the process). Each build ran while the other scheme's snapshot of the same size was served, so its peak
  includes that snapshot's tables; the replaced snapshot's JavaScript memory (SimplePIR's grids) is freed only when
  the garbage collector runs, which "resident once served" may or may not include. That row is therefore not a
  comparison of the schemes: at 2,000,000 it reads 4.70 GiB for IPIR+SP (built while SimplePIR's grids were served,
  which became garbage) and 1.14 GiB for SimplePIR (whose predecessor, IPIR+SP's native tables, was freed at once),
  with spreads of 1.94–5.32 and 0.92–5.23 GiB. The held bytes are the comparison. "Held" is what each served table
  says it holds (`ServerTable.heldBytes`, from the module's status): SimplePIR its grid's cells; IPIR+SP the add-on's
  cells and compiled packing matrices. The wallet's memory is the benchmark process's peak, which also holds the
  scan kernel, the ledger and the earlier wallet's leftovers.
- **Server time per call:** the module's request log line for the call (body decoded, every request answered, answer
  encoded). **Wallet times:** the client's own measurement of building the call body and of decoding the answer
  (IPIR+SP decodes only the wanted requests' answers, decision Q24; SimplePIR decodes all 32).
- **Machine:** Apple M4 Max, 16 cores, 48 GiB, macOS (Darwin 24.6.0), arm64. The machine was shared and loaded
  throughout: the 1-minute load average at the runs' starts was 7 to 27 (in each table's lead), part of it the
  benchmark's own 8 scan threads and the server's builds, part another agent's test suite running in Docker. Times are
  wall-clock under that load, and their spread is in the tables. No run failed, none was repeated or left out.
- **Run:** 2026-11-16, 05:01–05:57Z. The benchmark ran from the worktree at `c372e0aa`: real r1 as committed, real r2
  to 1,000,000 r2 with an uncommitted change that `e1f76372` then committed (the `compare` command's key-rows output,
  its test and a README line); from 1,000,000 r3 on at `e1f76372`. Nothing on the measured path differs.

Files beside this report: `runs/<scheme>-<size>-r<n>/results.json` (every number of a run, and the run's own
`REPORT.md`), `run-pair.sh`, `compare.json` (the aggregates), `TABLES.md` (every row of the comparison: 79 per size, the rows above
and the detail rows), `KEY-TABLES.md` (the tables of section 1), `micro.json` (section 9), `cert/` (section 7).

## 3. What IPIR+SP makes better

- **The wallet's download once per snapshot.** For the read and nullifier tables: 29,768 bytes of masks against
  16,875,520 bytes of setup data at the real size (0.18%), 44,616 against 23,166,976 at 100,000 (0.19%), 178,248
  against 63,045,632 at 1,000,000 (0.28%), 207,944 against 99,549,184 at 2,000,000 (0.21%). The path table's
  download before a first spend: 74,276 against 1,867,776 bytes at the real size, 193,060 against 18,677,760 at
  1,000,000, 267,300 against 37,355,520 at 2,000,000.
- **A wallet's whole first sync downloads less.** 3.0 MB against 20.0 MB at the real size (0.15×), 38.5 MB against
  101 MB at 1,000,000 (0.38×), 74.9 MB against 174.8 MB at 2,000,000 (0.43×). What is left is mostly the scan file (2.4 MB at the real size,
  34 MB at 1,000,000), the same for both schemes. Against downloading every output and nullifier (the naive baseline)
  a first sync moves 0.15 of it at the real size under IPIR+SP and 1.02 under SimplePIR.
- **Disk.** All artifacts of a snapshot take 0.59× SimplePIR's at the real size, 0.56× at 1,000,000 (698.7 MiB
  against 1.21 GiB) and at 2,000,000 (1.33 GiB against 2.39 GiB): IPIR+SP stores 16 bits of data per 16-bit cell (SimplePIR 9) and has no setup data.
- **The path table's call upload.** SimplePIR's path table is as wide as its noise check allows, so its requests are
  long: 277,316 bytes a query at the real size, 400,000 from 100,000 on; IPIR+SP's are 40,228 to 115,492 bytes (0.13×
  to 0.29× per call).
- **Server time per call at large sizes.** At 1,000,000 the path call takes 429 ms against 684 ms (0.63×); at
  2,000,000 every call is faster: read 176 ms against 250 ms (0.71×), nullifier 114 ms against 132 ms (0.86×), path
  530 ms against 1.27 s (0.42×). (IPIR+SP uses up to 16 threads per request here, SimplePIR 6: section 2.)
- **Build time at large sizes.** 17.6 s against 35.6 s at 1,000,000 (the path table's setup 6.3 s against 20.5 s),
  20.4 s against 63 s at 2,000,000 (0.32×; path setup 7.9 s against 40.3 s). At the real size and 100,000 both take 7.6–8.8 s, most of it the tree (4.7 s), which both
  share.
- **Wallet decode.** 0.12× to 0.29× SimplePIR's time for the read and nullifier calls (only the wanted answers are
  decoded).
- **Wallet memory at large sizes.** The wallet holds 178 KB of masks instead of 63 MB of setup data at 1,000,000 (208
  KB instead of 100 MB at 2,000,000); the benchmark process's peak during a sync was 663 MiB against 979 MiB at
  1,000,000 and 829 MiB against 1.15 GiB at 2,000,000.
- **A certified decoding bound** on every table measured (section 7): one answer decodes wrongly with probability at
  most 2^-268 or less. SimplePIR's own check is an 8σ bound on its noise (`checkNoise`), not a certificate; no
  certificate was computed for SimplePIR.

## 4. What IPIR+SP makes worse

- **Upload per call.** Every IPIR+SP query carries its own 27,648-byte key (decision Q5: a fresh secret and key per
  query), so a call of 32 queries uploads 884,736 bytes of keys whatever the table. At the real size a read call is
  1,287,336 bytes up against 317,096 (4.06×), a nullifier call 1,287,336 against 262,184 (4.91×); a whole first sync
  uploads 2.57 MB against 0.58 MB (4.4×). At 1,000,000 the gap is 1.41× (read) and 1.23× (nullifier); a whole first
  sync 2.98 MB against 2.24 MB (1.33×). At 2,000,000: read 1.23×, nullifier 1.61× (IPIR+SP's nullifier table has
  4,096 rows there, 52,772 bytes a query against SimplePIR's 32,768), a whole first sync 3.78 MB against 2.74 MB
  (1.38×).
- **Wallet time to build a call.** Each request is made on one thread of WebAssembly in about 8 ms at 2,048 rows (11
  ms at 4,096, 19 ms at 10,240), so a call takes 257 ms against SimplePIR's 29 ms at the real size (read, 8.8×; the
  nullifier call 23×), 365 ms against 64 ms at 1,000,000 (5.7×). SimplePIR's wallet used 8 worker threads. A whole
  first sync without its scan takes 782 ms against 263 ms at the real size (3.0×) and 1.38 s against 0.87 s at
  1,000,000. With the scan, which is the same for both (about 5 s at the real size, 66–70 s at 1,000,000), IPIR+SP's
  whole first sync took 1.05× (A) and 1.26× (B) SimplePIR's at the real size and 1.00× and 1.06× at 1,000,000.
- **Server time per call at small sizes.** A read call takes 35 ms against 9.9 ms at the real size (3.6×) and a
  nullifier call 31 ms against 5.0 ms (6.2×), with 16 rayon threads against SimplePIR's 6 workers: answering one query
  costs about 1 ms however small the table, for its key switching and packing. At 1,000,000 the two are close: read
  147 ms against 137 ms (1.08×), nullifier 111 ms against 72 ms (1.54×).
- **Server memory held by the tables.** The compiled packing matrices take 33,587,200 bytes per 2,048 columns: the
  three tables hold 280 MiB against 78 MiB at the real size (3.6×), 312 MiB against 114 MiB at 100,000 (2.7×), 1.43 GiB
  against 1.10 GiB at 1,000,000 (1.3×), 2.27 GiB against 2.19 GiB at 2,000,000 (1.03×). The server's peak during a
  build was 1.16× SimplePIR's at 1,000,000 (3.01 GiB against 2.60 GiB) and 1.17× at 2,000,000 (5.26 GiB against 4.51
  GiB); at the real size and 100,000 it was lower (0.72×). A restarted server builds every table again from its
  file (decision Q18): the masks and packing are not stored.
- **Download per call where the table is wide.** The path call's answer is 903,336 bytes against 58,408 at the real
  size (15.5×) and 2,345,128 against 583,720 at 1,000,000 (4.0×); the nullifier call's answer at 1,000,000 is 1.42×
  SimplePIR's. A later sync (artifacts cached) moves 0.75× SimplePIR's bytes at the real size but 1.09× at 1,000,000.
- **Build steps at small sizes.** The nullifier table's setup takes 397 ms against 216 ms at the real size (1.8×),
  the read table's 1.1–1.4×.
- **The smallest tables on disk.** IPIR+SP's smallest table is 2,048 × 2,048 cells (8 MiB): at the real size the
  nullifier table file is 8.00 MiB against SimplePIR's 6.47 MiB (1.24×), the other files smaller.
- **The path call's wallet time at large sizes.** 598 ms against 403 ms at 1,000,000 and 758 ms against 370 ms at
  2,000,000 (2.05×): IPIR+SP's path table there has 10,240 and 14,336 rows, and a request's time grows with them.

## 5. Where each scheme's size limits are

- **SimplePIR:** a table has at most 102,399 columns (its noise check `8 σ (p/2) √C < Δ/2`), so one query is at most
  409,596 bytes up; the rows are not limited by the check. The setup data a wallet downloads is 4,096 bytes per grid
  row: it grows with the square root of the records for the read and nullifier tables and, for the path table (as
  wide as allowed), with records ÷ 102,399. A padded build is refused when its estimate exceeds half the memory
  available (00053 Q57): on this machine a SimplePIR build padded to 10,000,000 was refused in an earlier run (its
  estimate is 12.67 GiB); 2,000,000 (estimate 2.89 GiB) ran here.
- **IPIR+SP:** at most 2^30 cells per table (upstream's 16-bit storage) and at most 32,768 rows (decision Q25: above
  that the certificate drops below 2^-128 with 49-bit queries). A 512-byte path record is 256 cells, so the path table
  holds at most 4,194,304 records: a padded build above 4.19 million at k = 16 is refused before anything is read
  (507 `table-too-large`), and so is 10,000,000 (it would need 2,560,000,000 cells). The read table (98-byte records)
  holds at most 21,911,552. The server holds 33,587,200 bytes of packing per 2,048 columns besides the cells; the
  padded-build estimate at 2,000,000 is 3.79 GiB. A query's upload grows by 49 bits per row from 40,228 bytes at
  2,048 rows to 228,388 bytes at 32,768 rows, and its answer by 22 bits per column.

## 7. Correctness certificate on the project's own tables (review finding F3)

Upstream's `native_noise` example analyses a table of its own random cells, so it cannot read a project table. The
example `ipir/core/examples/noise_report.rs` reads a stored table file, sets the table up as the server does (the seed
from the manifest, the file's SHA-256 as the setup's snapshot input, the crate's profile), refuses unless its setup
identifier equals the crate's and the masks it builds equal the stored ones byte for byte, and writes upstream's noise
report (`native-noise-two-mask-rounded-v1`). Upstream's `certify_native.py --screens` (the vendored copy, unchanged)
then bounds, with exact rational arithmetic and the sampler's true distribution, the probability that any coefficient
of one answer leaves the decoding interval (`cert/run-cert-snapshot.sh`). The bound is
per answer and per table; it does not accumulate over requests. The worst-case-query column is upstream's screen with
every cell 0xFFFF in the query term on the same masks, not a certificate.

| Snapshot | Table | Cells R × C | One answer fails with probability at most | Meets 2^-128 | Worst-case-query screen | File |
|---|---|---|---|---|---|---|
| 1m | nullifier | 2,048 × 12,288 | 2^-288 | yes | 2^-283 | `cert/cert-1m-nullifier.json` |
| 1m | path | 10,240 × 26,624 | 2^-268 | yes | 2^-246 | `cert/cert-1m-path.json` |
| 1m | read | 4,096 × 12,288 | 2^-286 | yes | 2^-276 | `cert/cert-1m-read.json` |
| real | nullifier | 2,048 × 2,048 | 2^-300 | yes | 2^-295 | `cert/cert-real-nullifier.json` |
| real | path | 2,048 × 10,240 | 2^-291 | yes | 2^-288 | `cert/cert-real-path.json` |
| real | read | 2,048 × 2,048 | 2^-303 | yes | 2^-298 | `cert/cert-real-read.json` |

The real snapshot is `0d3644b0…`, the padded one `7372f6d3…` (built by the 1,000,000 r1 run). Every table meets
upstream's 2^-128 gate by a wide margin. The bound falls with the row count (2,048 → 10,240 rows: 2^-303 → 2^-268), as
the review found on upstream's tables. The padded tables' cells are random 16-bit noise, like upstream's own tables;
the real tables' cells are records with zero padding.

## 11. What was not measured

- **A real network.** Every request went over 127.0.0.1; round trips include no network latency or bandwidth limit.
  On a slow link SimplePIR's per-snapshot download and IPIR+SP's per-call upload weigh more than here.
- **Equal thread budgets.** IPIR+SP's server used up to 16 threads per request, SimplePIR's 6; IPIR+SP's wallet one
  thread, SimplePIR's 8 (section 10 gives the wallet's request time at 8 threads). No run fixed the threads to the same count, and CPU time was not measured, only wall time.
- **An idle machine.** All timings were taken while other work ran on the machine (load average 7–27).
- **The transfer.** Only the path read a spend makes; no transaction was built or proved here (task 4.3 covers
  `send`).
- **The browser and the GPU** (phases 6 and 7), and a phone.
- **10,000,000 entries** (estimates only, section 5), and IPIR+SP above 2,000,000.
- **A certificate for SimplePIR**, and IPIR+SP certificates at 100,000 and 2,000,000 (only the real and 1,000,000
  snapshots were certified).
- **Resident memory without the replaced snapshot's garbage:** no collection was forced in the server.
