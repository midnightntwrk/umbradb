The problem

What the wallet needs, and what the server must not learn

Today a wallet either gives its viewing key to an indexer, which then sees every coin it owns, or replays every ledger event itself. This proof of concept is a third way.

The wallet needs to learn

  • which shielded outputs on the chain are its own;
  • for each one, its commitment, its ciphertext and its Merkle path: to read the coin and, later, to spend it;
  • whether each coin is already spent: whether its nullifier is on the chain.

The server must not learn

  • the wallet's keys;
  • which outputs are the wallet's;
  • which records the wallet reads;
  • which nullifiers it looks up, so which of its coins are spent.
Scope. Privacy only. The server is assumed curious: it records everything it receives and tries to learn from it. It is assumed to answer correctly; checking that its answers are right is outside this proof of concept. No protocol change: everything runs on Midnight's existing outputs and nullifiers.
The approach

Three mechanisms, and why each one hides the wallet

MechanismStepsWhy the server learns nothing
The same download for every wallet: the manifest, the scan file, the block roots, the setup data, the tail2 (files), 6 (tail)What is downloaded does not depend on the wallet. The server sees "someone downloaded the snapshot", as from every other wallet.
Local trial decryption of every output's scan entry3 (scan)Nothing is sent. The wallet tests all entries with its own key, on its own device.
Private information retrieval (SimplePIR), with a fixed number of query vectors per call4 (records), 5 (nullifiers)Each query vector is A·s + e + Δ·u. Without the wallet's secret s, it cannot be told apart from random numbers, so the server cannot see which column it asks for. Every call has the same number of vectors, so the count says nothing either.
The server still multiplies its whole table by each vector and sends back an answer; only the wallet, which holds s, can turn that answer into the column it asked for.

Step 0 · The server builds a snapshot · 2 of 3 Server

The public matrices A, A′ and the setup data H, H′ gpu

A is a matrix of random numbers, one row per table column and n columns (n = 2 here, 1,024 on the real server). It is generated from a random seed written in the manifest, so every wallet rebuilds the same A; nobody downloads it. A is public: the query is hidden by the wallet's secret s, not by A. The setup data H = table × A lets a wallet decode an answer.

The plan

  • Output 2 is in column 0, output 6 in column 2. PIR returns whole columns, so the wallet will get r0–r2 and r6–r8 and keep r2 and r6.
  • One query vector fetches one column. If the wallet sent only 2, the server would learn it owns about 2 outputs; a wallet with nothing would send none.
  • So every call carries the same number of vectors: 3 in this example, 32 on the real server. The wallet adds column 1 as padding, at random; its answer is thrown away. Which column the padding asks for makes no difference: the server cannot see the column of any vector.

Step 4 · Fetch my records by PIR · 4 of 5 Wallet

Decoding: subtract H·s, divide by Δ, round

Review

Why the server learns nothing, step by step

StepWhat is sentWhy it reveals nothing
1 Keysnothing—
2 Filesrequests for the snapshot's manifest and filesEvery wallet asks for the same files; the download does not depend on the keys.
3 ScannothingThe whole scan file is tested on the device.
4 Recordsq = A·s + e + Δ·u, a fixed number per callWithout s, A·s + e looks random (Learning With Errors), so q hides u, the column. The count is fixed, so it hides how many outputs the wallet owns. Removing A·s needs s, which never leaves the wallet.
5 Nullifiersthe same, over the nullifier tableThe same argument; the nullifiers are computed and compared on the device.
6 Taila request for the tailEvery wallet gets the same bytes and checks them on the device.
The real parameters: n = 1,024, q = 232, noise σ = 6.4, values of 9 bits, 32 vectors per call; SimplePIR's published choice for this security level. The slides use n = 2 and q = 65,536 so the numbers fit.
Review

What still shows, and what is out of scope

WhatWhyHow to close it
A rough count above 32A wallet needing more than 32 columns (or buckets) sends a second call, so the server learns "more than 32".Always send a fixed number of calls, or raise the vectors per call; costs bytes for everyone.
When and how often a wallet syncs, and its IP addressPIR hides what is asked, not that someone asked.A relay or Tor; syncing on a regular schedule.
Timing around a spendIf the same operator runs the node a transaction is sent to, "this client synced, then a new nullifier appeared" can be correlated.Submit transactions through another path.
Correct answers (out of scope)A dishonest server cannot learn which coins a wallet has, but it could answer wrongly, for example "unspent" for a spent coin.Checks against a trusted root, or attestation; not part of this proof of concept. A wrong "unspent" shows when the spend is refused on chain.
