Private shielded sync, step by step

The client's own code runs in this page's worker. The keys never leave it: only the requests listed on the right reach the server. Each step shows what it did and its debug output. How each step works →

0Load the client

Fetches the scan kernel (WebAssembly; its SHA-256 is checked against the committed one) and the Midnight ledger package (WebAssembly), and asks the page's server which debug routes it has.

1Wallet keys

BIP-39 mnemonic → seed → HD path m/44'/2400'/0'/3/0 → Zswap secret keys (the ledger's ZswapSecretKeys.fromSeed). The encryption secret key's scalar is what the scan uses.

2Get the files

The manifest, then the four files every wallet downloads alike: the scan file (36 bytes per output), the block roots, and the public artifact of the read and nullifier tables (SimplePIR's setup data, or IPIR+SP's two masks per table). Each is checked against the manifest's SHA-256. On an IPIR+SP snapshot the wallet's WebAssembly is fetched too, and compiled only if its SHA-256 is the committed one.

builds a new snapshot on the server, then gets its files. A table size pads the scan file and the PIR tables to that many entries, the real data spread among noise, to time each step with more data. The scheme builds the same height under SimplePIR or IPIR+SP, so both can be compared on the same data.

3Find my outputs (scan)

Tests every scan entry locally: point × encryption secret key, Poseidon, compare 4 bytes of element 0. Nothing is sent.

4Fetch records by PIR (commitment prefix, ciphertext)

Reads the read-table records of the positions privately: the calls carry encrypted requests (SimplePIR: query vectors, one per column asked for; IPIR+SP: one request per row asked for, each with its own key), padded with random columns or rows. A record is 98 bytes: the commitment's first 16 bytes and ciphertext elements 1–5 shrunk to 82 bytes; the wallet rebuilds the elements from its own pads. Leave empty to fetch the scan's matches, or pick positions to test with any output. Each row's Compare button checks that record against the database (debug).

5Check nullifiers by PIR

Looks up the found coins' nullifiers in the snapshot's nullifier table, privately (one bucket per nullifier, padded). Add nullifiers by hand to test with any spend.

6Merkle paths by PIR (only to spend)

A sync does not read Merkle paths: a wallet reads its coin's lower path from the path table only when it spends. The first read downloads the path table's setup data or masks (once per snapshot). Leave empty for the wallet's snapshot coins, or enter positions. Each path is checked against its block's root.

7Get the tail

Everything after the snapshot, in full: the partial block's commitments, new outputs (scanned here too), spends, block roots. It also checks the full 32-hash Merkle path of each position read (with a path from step 6, or from the tail), against the tail's root, as a spend would build it.

8Coins and balance

The coins found so far, their nullifiers and whether they are spent.

9Dust: get the file and my first coins

Dust needs the mnemonic of step 1: its Dust seed (HD m/44'/2400'/0'/2/0) gives the Dust key. Gets the Dust file's manifest and each chunk (every Dust spend of the current ledger era, about 9 bytes each: a 4-byte nullifier prefix, the declared time, the fee and the new commitment's position), checking each against the manifest's SHA-256; a chunk kept from an earlier run is not downloaded again. Then the Dust parameters, and this wallet's first coins and generation updates: the one request that names the wallet (its Dust public key).

10Dust: walk my chains

For each first coin, computes the coin's nullifier, finds its 4-byte prefix in the file from the first entry above the coin's own position, derives the next coin from that entry's time, fee and position (the ledger's successorDustUtxo), and goes on from the entry after. Nothing is sent. A prefix can match another wallet's spend: step 11 checks each chain's end.

11Dust: check each chain by PIR

Gets the Dust check table's manifest and public artifact (once per table), then walks again and reads, by PIR, the commitment at each chain's last coin's position, all chains in calls padded to the same number of requests, so the server cannot tell which positions or how many chains. A commitment that is not the coin's drops that match, the search goes on after it, and the new end is checked in a further call. A chain without a spend needs no check; a coin newer than the table is not checkable yet. A wallet with nothing to check still sends one call.
